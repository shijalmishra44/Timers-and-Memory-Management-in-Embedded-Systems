1. Introduction & Scope

1.1 What is an embedded timer?

A timer is a hardware peripheral containing a free-running or programmable binary counter that is driven by a (typically prescaled) clock derived from the system clock or an external source. Because the counter is implemented in silicon, it counts deterministically and independently of the CPU, which makes it the fundamental building block for timing, event counting, waveform generation and time measurement in every microcontroller — from an 8-bit 8051 to a 32-bit ARM Cortex-M7.

1.2 What is memory management in an embedded system?

Memory management in embedded firmware is the disciplined partitioning and lifetime control of the limited on-chip memory resources: non-volatile program memory (Flash), volatile data memory (SRAM), and non-volatile data storage (EEPROM/emulated EEPROM). It covers the linker-defined memory map, the stack, the heap, static/global storage, memory pools, and the runtime policies (allocation, protection, monitoring, recovery) that keep the firmware deterministic and safe.

1.3 Why these two topics are studied together

They are tightly coupled in real firmware:

  • The RTOS tick is generated by a hardware timer (SysTick / TIMx); that tick drives every task delay, timeout and time-slice — i.e., the timer is the heartbeat of the scheduler.
  • Every timer interrupt service routine consumes stack. A too-small stack plus a high-frequency timer ISR is the classic cause of random resets in the field.
  • Buffer management (DMA rings, communication buffers, memory pools) is usually driven by timer-triggered sampling and transmission events.
  • Both are favourite areas for GATE numericals and core-company interview questions because they expose whether a candidate truly understands hardware–software interaction.

1.6 Classification

Classification of timers

  • By counting direction: up-counter, down-counter, up/down (centre-aligned)
  • By width: 8-bit, 16-bit (most common), 24-bit (SysTick), 32-bit
  • By function: basic time-base, general-purpose, advanced-control (complementary outputs + dead-time), watchdog (IWDG/WWDG), RTC
  • By clock source: internal APB clock, external event counter, external clock input
  • By implementation: hardware timer vs software (loop) delay vs RTOS software timer

Classification of memory in an MCU

  • Program memory: on-chip Flash, ROM, OTP
  • Data memory: SRAM (DTCM, CCM, AHB-SRAM), external SDRAM/PSRAM
  • Non-volatile data: EEPROM, emulated EEPROM in Flash, FRAM
  • Allocation class: static (link-time) vs automatic (stack) vs dynamic (heap)
  • By access: CPU-only, DMA-accessible, cacheable/non-cacheable

2. Fundamental Operating Principle

2.1 The timer chain

Every general-purpose timer follows the same signal chain:

fclk  →  Prescaler (÷ N = PSC+1)  →  ftick  →  Counter CNT (0 … ARR)  →  Update / Compare / Capture

The counter advances by one count for every timer tick. When CNT passes ARR it wraps around and sets the update flag (UIF), which can raise an interrupt or a DMA request. If a compare value CCR is programmed, a compare event occurs when CNT = CCR, and the output pin can be set, cleared or toggled — this is precisely how PWM is generated.

2.2 The three canonical timer jobs

  1. Time base / periodic interrupt: count a known time and interrupt the CPU (RTOS tick, ADC sampling trigger, software debounce tick).
  2. Waveform generation (output compare / PWM): produce a precise square wave whose frequency and duty are set by ARR and CCR (motor drive, LED dimming, servo control, class-D audio).
  3. Waveform measurement (input capture): latch the counter on external edges to measure pulse width, period, frequency, duty cycle, or to decode a rotary encoder.

2.3 The embedded memory model

At link time the toolchain splits the program into sections and places them according to a linker script (GNU LD) or scatter file (ARM Compiler):

SectionContentsTypical locationVolatile?
.textExecutable instructionsFlash / ROMNo
.rodataString literals, const tables, lookup tablesFlash / ROMNo
.dataInitialised global/static variables (int x = 5;)RAM (init values stored in Flash and copied at startup)Yes
.bssUninitialised/zero-initialised globals & statics (int x;)RAM (zeroed at startup)Yes
Heapmalloc/calloc/realloc blocksRAM, grows upwardYes
StackFunction frames, locals, saved registers, ISR contextTop of RAM, grows downwardYes
Key insight: .data costs twice — it occupies Flash (to store the initial value) and RAM (for the live variable). A large initialised constant table declared without const can therefore silently consume both Flash and precious SRAM.

2.4 Startup sequence (what happens before main())

  1. Reset vector fetches the initial stack pointer (MSP) from address 0x0000_0000.
  2. Startup code copies the .data initialisers from Flash to RAM.
  3. Startup code zeroes the entire .bss region.
  4. Heap and stack pointers (_end, __initial_sp) are set from the linker symbols.
  5. System clock / PLL is configured; main() is called.

If the linker script is wrong, this sequence corrupts memory before the first line of application code ever runs — a very common source of "it works on the dev board but not on my custom PCB" bugs.

4. Working Principle & Detailed Explanation

4.1 Timer operation, step by step

  1. Clock selection: the timer is fed from an internal bus clock (e.g., APB1/APB2) or from an external pin. The clock frequency after the peripheral clock divider is fclk.
  2. Prescaling: PSC divides fclk by (PSC+1). Choosing PSC = 71 with fclk = 72 MHz gives ftick = 1 MHz, i.e. ttick = 1 µs.
  3. Counting: CNT increments once every ttick. In up-counting mode it runs 0, 1, 2, … ARR, then wraps to 0.
  4. Update event: on wrap-around the UIF flag is set. With the update interrupt enabled, the CPU vectors to the ISR — this is the periodic time base.
  5. Compare event: when CNT = CCR, the channel flag is set and the output pin can be driven according to the output mode (set / clear / toggle / PWM1 / PWM2).
  6. Capture event: in input-capture mode, an external edge copies CNT into CCR instantly (hardware, no software latency), giving sub-microsecond measurement accuracy.

4.3 DC and AC behaviour of the memory subsystem

Although "memory management" is not an AC circuit topic, it has a clear static/dynamic split that students should distinguish:

  • Static (link-time) behaviour: section sizes, base addresses, alignment, and the Flash→RAM copy of .data. These are fixed and verified by the .map file.
  • Dynamic (run-time) behaviour: stack depth varies with call nesting and ISR entry; heap occupancy varies with allocation/free patterns. These must be bounded by design, not merely observed.

4.4 Important assumptions and approximations

  • The timer clock is assumed exact. In reality the HSI oscillator may be ±1 % and the crystal ±20–50 ppm; PWM frequency and baud rate inherit that error.
  • Prescaler and ARR are assumed to be buffered (shadow registers) so that a mid-period write does not create a glitch. On many MCUs the ARR preload must be explicitly enabled (ARPE bit).
  • Interrupt latency and ISR execution time are neglected in the ideal timing equations; in practice they add jitter of tens to hundreds of CPU cycles.
  • The stack is assumed to have enough headroom for the worst-case nested ISR — this must be measured, not guessed.

4.5 Advantages, limitations and design considerations

Timers — advantages

  • Fully hardware: no CPU load for counting or PWM generation
  • Deterministic, crystal-accurate timing
  • Multiple simultaneous functions (PWM, capture, time base) on one peripheral
  • Can trigger ADC/DMA autonomously, reducing interrupts

Timers — limitations

  • Limited number of timer peripherals and channels
  • Resolution × range trade-off: you cannot have 1 µs resolution and 1 hour range with one 16-bit timer
  • Counter wrap-around must be handled in capture/period software
  • Shared interrupts and priority inversion can add jitter

Dynamic allocation — advantages

  • Flexible memory use when object lifetime is unknown
  • Convenient for variable-length buffers and message queues

Dynamic allocation — limitations

  • Non-deterministic execution time (unbounded worst case)
  • Fragmentation → allocation failure after long uptime
  • Memory leaks in firmware with no OS to reclaim memory
  • Not permitted in many safety standards (MISRA C Dir 4.12, DO-178C, IEC 61508)

4.6 Common student misconceptions

  1. "The prescaler only slows things down — it's free." No: increasing PSC also reduces resolution. With PSC = 9999 you cannot resolve 1 µs events any more.
  2. "A 16-bit timer can only time 65535 µs." False — the prescaler extends the range at the cost of resolution; combined range is (PSC+1)×(ARR+1) ticks.
  3. "malloc is fine, I tested it for an hour." Fragmentation and leaks typically appear after days of uptime with fragmented heap usage patterns.
  4. "Stack overflow will show up as a crash." Often it silently corrupts .bss or heap data, producing bizarre, unrelated bugs.
  5. ".bss takes no Flash, therefore it is free." True for Flash, but it still consumes RAM — usually the scarcest resource.
  6. "Global variables are always in .data." Only initialised ones; uninitialised globals go to .bss.
  7. "A local array is safe because it is small." A 512-byte local array inside an ISR running at 10 kHz will consume far more stack than expected if the ISR is nested.

6. Mathematical Equations & Derivations

6.1 Timer tick and period

ftick = fclk / (PSC + 1)    [Hz]
ttick = 1 / ftick = (PSC + 1) / fclk    [s]

Variables: fclk = timer input clock (Hz), PSC = 16-bit prescaler value (0…65535, dimensionless), ftick = counter clock (Hz), ttick = time per count (s).

6.2 Update (overflow) period and frequency

Tupdate = (ARR + 1) × (PSC + 1) / fclk   [s]

fupdate = fclk / [ (PSC + 1)(ARR + 1) ]   [Hz]

Derivation: the counter takes (ARR+1) ticks to go from 0 to ARR and wrap (including the 0 state). Each tick lasts ttick = (PSC+1)/fclk. Multiplying gives the update period. The "+1" is because the counter passes through (ARR+1) distinct states in one full cycle.

Applicability: up-counting edge-aligned mode with ARR preload enabled.

Limiting cases: PSC = 0 and ARR = 0 → the counter toggles every tick (fupdate = fclk/1). Maximum period for a 16-bit timer: Tmax = 65536 × 65536 / fclk.

6.3 PWM duty cycle and resolution

Duty (%) = [ CCR / (ARR + 1) ] × 100    (PWM mode 1, edge-aligned)

Ton = CCR × (PSC + 1) / fclk   [s]

Duty resolution = 1 / (ARR + 1)   (fraction of full scale)

Physical meaning: the average output voltage delivered to a load is Vavg = D × VDD, so a 3.3 V PWM at 60 % duty behaves (for a slow load such as a motor or an LED) like a 1.98 V DC source.

Trade-off: for a fixed fPWM, increasing the clock (or decreasing PSC) increases (ARR+1) and therefore improves duty resolution.

6.4 Centre-aligned PWM

TPWM(centre) = 2 × ARR × (PSC + 1) / fclk   [s]   (STM32 reference-manual convention)

In centre-aligned mode the counter counts up to ARR and back down to 0, so one PWM period contains two ramps and the output is symmetric about the period centre. The benefits are reduced low-order harmonic content (important for motor drives) and inherently aligned complementary edges. The cost is that the achievable frequency is roughly half that of edge-aligned mode for the same ARR.

6.5 Input-capture measurement

ΔN = (CAP2 − CAP1)   [counts]   (add 65536 if the counter wrapped)

Tsignal = ΔN × ttick = ΔN × (PSC + 1) / fclk

fsignal = 1 / Tsignal = fclk / [ ΔN × (PSC + 1) ]

Assumption: ΔN is less than one full counter cycle (no more than one wrap between the two captures). If the counter wraps, the software must add (ARR+1) to the difference.

Measurement resolution is exactly one timer tick, ttick, and does not depend on interrupt latency.

6.6 SysTick / RTOS tick configuration

RELOAD = fclk × Ttick − 1

For a 1 ms tick at 16 MHz: RELOAD = 16 000 000 × 0.001 − 1 = 15 999

SysTick is a 24-bit down-counter, so RELOAD ≤ 16 777 215. At 16 MHz the maximum single-shot tick period is 16777216/16e6 ≈ 1.048 s.

6.7 Watchdog timeout

TWDT = (PSC + 1) × (RLR + 1) / fLSI

For an independent watchdog clocked by a 32 kHz LSI with PSC = 63 and RLR = 1249: TWDT = 64 × 1250 / 32000 = 2.5 s. Firmware must kick the watchdog at less than half this interval to guarantee it never times out during normal execution.

6.8 UART baud-rate generation (a classic timer application)

BRR = fclk / (16 × Baud)   (oversampling by 16)

Baudactual = fclk / (16 × BRR)

Error (%) = (Baudactual − Baudtarget) / Baudtarget × 100

Keep the absolute error below ±2 % (ideally below ±1 %) to survive 10-bit framing with the far-end tolerance included.

6.9 Memory equations

RAMused = .data + .bss + Heappeak + Stackpeak

RAMfree = RAMtotal − RAMused   (must remain > 0 with margin)

Stackworst = Σ (frameISR_i)nested + framemain + contextsave + margin

Heap utilisation = Heapallocated / Heapsize × 100 %

Largest-free-block ratio = Largest free block / Total free bytes

Physical meaning: the third equation is the design rule for stack sizing. A practical margin is 30–50 % (or 512 bytes, whichever is larger) on top of the measured worst case. The last equation quantifies fragmentation: a ratio near 1.0 means healthy, a ratio near 1/N means the heap is shattered into N pieces and the next allocation will likely fail.

6.10 Flash and RAM cost of .data

Flash needed = .text + .rodata + |.data|
RAM needed = |.data| + |.bss| + heap + stack

This is why large constant lookup tables must be declared const (they then live only in Flash/.rodata) rather than as plain globals.

7. Solved Numerical Problems

Problem 1 — Easy Periodic interrupt from a general-purpose timer

Given: A 16-bit timer is clocked at fclk = 72 MHz. PSC = 71 and ARR = 999.
Find: (a) the timer tick period, (b) the update-interrupt period, (c) the interrupt frequency.

Step 1 — Tick period:

ttick = (PSC + 1) / fclk = 72 / 72 × 106 = 1 × 10−6 s = 1 µs

Step 2 — Update period:

T = (ARR + 1) × ttick = 1000 × 1 µs = 1 ms

Step 3 — Interrupt frequency:

f = 1 / 1 ms = 1 kHz

Engineering interpretation: this is the standard 1 ms "system tick" configuration. At 1 kHz the ISR must execute in far less than 1 ms — a practical budget is under 10 % of the period, i.e. under 100 µs, otherwise CPU throughput is lost to interrupt overhead.

Problem 2 — Moderate Designing a 50 Hz servo PWM

Given: fclk = 84 MHz, required PWM frequency = 50 Hz, required duty = 60 %.
Find: suitable PSC, ARR, CCR values and the resulting duty resolution.

Step 1 — Choose the tick: select PSC = 83 → ftick = 84 MHz / 84 = 1 MHz → ttick = 1 µs.

Step 2 — Period count: T = 1/50 Hz = 20 ms = 20 000 µs.

ARR + 1 = T / ttick = 20 000 → ARR = 19 999

Step 3 — Compare value:

CCR = Duty × (ARR + 1) = 0.60 × 20 000 = 12 000

Step 4 — Resolution:

Duty resolution = 1 / 20 000 = 0.005 % → 20 000 discrete steps

Engineering interpretation: 1 µs resolution corresponds to 0.005 % of the 20 ms period — vastly finer than the ~1 µs pulse-width granularity a hobby servo needs. For hobby servos you would actually set CCR between 1000 (1 ms, −90°) and 2000 (2 ms, +90°), keeping the 20 ms period fixed. Note that ARR = 19 999 fits comfortably in a 16-bit register (max 65 535).

Problem 3 — Moderate Input-capture frequency measurement (GATE-style)

Given: A timer with fclk = 8 MHz and PSC = 3 is used in input-capture mode on the rising edges of an unknown signal. Two consecutive captures read CAP1 = 1200 and CAP2 = 5400. The counter did not wrap between the captures.
Find: the signal period and frequency.

Step 1 — Tick period:

ttick = (3 + 1) / 8 × 106 = 4 / 8 × 106 = 0.5 µs

Step 2 — Count difference:

ΔN = 5400 − 1200 = 4200 counts

Step 3 — Period:

T = 4200 × 0.5 µs = 2100 µs = 2.1 ms

Step 4 — Frequency:

f = 1 / 2.1 ms = 476.19 Hz

Engineering interpretation: the measurement is limited only by the 0.5 µs tick, so the resolution is 0.5/2100 ≈ 0.024 %. This is why input capture is used for tachometers and ultrasonic sensors instead of polling the pin in software — software polling would add the ISR latency (tens of microseconds) as an error term.

Problem 4 — Moderate SRAM budget check

Given: an MCU with 20 KB of SRAM and the following linker report: .data = 1.5 KB, .bss = 6.2 KB, heap pool = 4 KB, stack reservation = 2 KB.
Find: the free RAM remaining, and state whether the design is safe.

Step 1 — Total used:

1.5 + 6.2 + 4.0 + 2.0 = 13.7 KB

Step 2 — Free RAM:

20 − 13.7 = 6.3 KB free (31.5 % headroom)

Step 3 — Safety assessment: a 31.5 % margin is acceptable for a first prototype. However, the heap and stack figures are reservations, not measurements. The stack must be verified by the paint/watermark method under worst-case interrupt load, and the heap must be verified by peak-usage instrumentation over a long soak test.

Problem 5 — Difficult Worst-case stack sizing

Given: A Cortex-M firmware has a main loop whose deepest call chain uses a 256-byte frame. Three interrupts can nest: an ADC ISR with 96 bytes of locals, a UART ISR with 128 bytes, and a timer ISR with 64 bytes. Each exception entry automatically pushes 8 registers (32 bytes) plus 8 bytes of alignment padding on a floating-point context save.
Find: the minimum recommended stack size.

Step 1 — Worst-case nested ISR frames (assume all three nest):

ISR locals = 96 + 128 + 64 = 288 bytes
Exception frames = 3 × (32 + 8) = 120 bytes
ISR total = 288 + 120 = 408 bytes

Step 2 — Add the main-context frame:

408 + 256 = 664 bytes

Step 3 — Add a 30 % safety margin:

664 × 1.30 = 863.2 bytes → round up to 1024 bytes (1 KB)

Engineering interpretation: the naive estimate of "a few hundred bytes" would overflow on the first occasion that all three interrupts nest. Rounding up to a power of two also makes the stack easier to align and to monitor with a watermark pattern such as 0xDEADBEEF. Verify at runtime with uxTaskGetStackHighWaterMark() (FreeRTOS) or by painting the stack and measuring the untouched region.

Problem 6 — Difficult UART baud error with a timer clock

Given: fclk = 16 MHz, target baud = 9600, oversampling = 16.
Find: BRR, actual baud, and percentage error.

Step 1: BRR = 16 × 106 / (16 × 9600) = 104.1667 → integer BRR = 104.

Step 2: Baudactual = 16 × 106 / (16 × 104) = 9615.38 baud.

Step 3: Error = (9615.38 − 9600)/9600 × 100 = +0.16 %.

Engineering interpretation: 0.16 % is well within the ±2 % budget, so communication will be reliable. Accumulated error over a 10-bit frame is about 1.6 % of one bit period — safely below the 50 % sampling-point margin. Using a fractional baud-rate register (BRR with a 4-bit fraction field) reduces this error further.

9. Core Electronics Company Interview Preparation

Click any question to expand a model answer written at the depth expected in semiconductor, embedded-product and hardware-validation interviews.

Q1. What is the fundamental difference between a hardware timer and a software delay loop?
A software delay loop burns CPU cycles doing nothing, is not accurate (it depends on compiler optimisation, cache behaviour, interrupt load and clock frequency), and blocks all other work. A hardware timer is an independent silicon counter that runs in parallel with the CPU; the CPU is free to sleep or perform other tasks, and the timing accuracy depends only on the clock source (typically a crystal, tens of ppm). Practical consequence: a for(i=0;i<100000;i++); delay can vary by an order of magnitude between a debug and a release build, whereas a timer-based delay does not change at all.
Q2. How does a prescaler affect both the range and the resolution of a timer?
The prescaler divides the input clock by (PSC+1), so the tick period becomes (PSC+1)/fclk. Increasing PSC lengthens the maximum measurable/generatable time (range = (PSC+1)(ARR+1) ticks) but simultaneously makes each tick coarser, so the smallest resolvable time interval grows proportionally. The product of range and resolution is constant for a given counter width and clock: you cannot improve both at once. If you need both fine resolution and a long range, use a 32-bit timer, cascade two timers, or count overflows in software.
Q3. Explain input capture versus output compare with a practical example of each.
Output compare compares CNT against CCR and acts on the output pin (set/clear/toggle/PWM). It generates timing. Example: generating a 20 kHz PWM for a BLDC motor gate driver.
Input capture copies CNT into CCR when an external edge is detected. It measures timing. Example: measuring the echo pulse width from an HC-SR04 ultrasonic sensor, or measuring the period of a tachometer signal to compute RPM. Both use the same CCR registers but the data direction and the trigger source are opposite.
Q4. What is the difference between an independent watchdog and a window watchdog?
An independent watchdog (IWDG) is clocked by a dedicated low-speed oscillator (LSI, ~32 kHz) and therefore keeps running even if the main clock or PLL fails. It resets the MCU if it is not refreshed within the timeout — it only detects "too late". A window watchdog (WWDG) is clocked from the main clock and resets the MCU if the refresh occurs either too late or too early, i.e. outside a defined window. The window feature catches runaway code that refreshes the watchdog far too often (for example, a loop that crashes into the refresh routine). Safety-critical designs often use both.
Q5. Your PWM output has the correct frequency but the duty cycle is wrong. How do you debug it?
A systematic checklist:
1. Verify CCR is written to the active channel (CCR1 vs CCR2) and that the correct channel is enabled in the capture/compare enable register.
2. Check the output mode: PWM mode 1 is active-high while PWM mode 2 is inverted — a 40 % setting can appear as 60 %.
3. Confirm the compare preload bit — without it, a CCR write can take effect immediately and produce a distorted first cycle.
4. Confirm the polarity bit (CCxP) and the GPIO alternate-function configuration; a wrong AF number leaves the pin as a plain GPIO.
5. Check whether ARR was changed after CCR was computed; duty = CCR/(ARR+1) depends on both.
6. Measure with a scope on the pin itself, not through a long jumper, to rule out loading and ringing.
Q6. Why is malloc discouraged in embedded firmware?
Four reasons: (i) non-determinism — the worst-case execution time of malloc is unbounded, which breaks real-time deadlines; (ii) fragmentation — after a long uptime the heap may have plenty of total free bytes but no contiguous block large enough; (iii) leaks — embedded firmware typically has no OS to reclaim memory, so a single missed free permanently loses RAM; (iv) certification — MISRA C and safety standards such as DO-178C and IEC 61508 restrict or forbid dynamic allocation. The preferred alternatives are static allocation, fixed-size memory pools, ring buffers, and RTOS heap schemes that never free (e.g. FreeRTOS heap_1).
Q7. What is heap fragmentation and how do you prevent it?
Fragmentation is the condition where free memory exists but is split into blocks smaller than the requested allocation, so an allocation fails despite sufficient total free space. It is aggravated by mixing allocation sizes and by long-lived allocations interleaved with short-lived ones. Prevention: (1) use fixed-size memory pools so every block is identical and any free block satisfies any request; (2) allocate all long-lived objects at start-up ("allocate once, never free"); (3) use a coalescing allocator (FreeRTOS heap_4/5, TLSF) that merges adjacent free blocks; (4) periodically monitor the largest-free-block ratio rather than total free bytes.
Q8. How do you detect and prevent stack overflow on an MCU with no MMU?
Detection: (a) stack painting — fill the stack with a known pattern (e.g. 0xDEADBEEF) at start-up and measure how much remains untouched (uxTaskGetStackHighWaterMark() does this in FreeRTOS); (b) a stack canary — place a magic value at the stack limit and check it periodically; (c) a hardware watchpoint or the MPU, configured to make the region below the stack fault on access; (d) the Cortex-M stack-limit check registers (PSPLIM/MSPLIM) on newer cores.
Prevention: size the stack from the measured worst case plus 30–50 % margin, avoid large local arrays and printf in ISRs, avoid deep recursion, and keep ISR nesting bounded by priority design.
Q9. Explain the role of the linker script and how you would place a DMA buffer in a specific memory region.
The linker script (GNU LD) or scatter file (ARM Compiler) defines the memory regions (FLASH, RAM, CCMRAM, etc.), their base addresses and sizes, and maps input sections from object files into those regions. It also defines symbols such as _sdata, _edata, _sbss, _ebss, _estack used by the startup code.
To place a buffer in a specific region: define a named section in the linker script (e.g. .dma_buffer : { *(.dma_buffer) } > RAM_D1), then in C use __attribute__((section(".dma_buffer"))) uint8_t buf[1024];. On STM32F4 this is how you keep a buffer out of CCM RAM, which the DMA controller cannot access.
Q10. Why must a variable shared between an ISR and main code be declared volatile?
Without volatile, the compiler is entitled to assume that a variable cannot change except through visible code. It may therefore cache the value in a register and never re-read it, producing an infinite loop such as while(!flag); where flag is set by the ISR. volatile forces a memory access on every read/write. Note that volatile does not provide atomicity or mutual exclusion — for multi-byte shared data you still need critical sections, atomics, or a lock-free single-writer/single-reader design.
Q11. What causes timer interrupt jitter and how can it be reduced?
Jitter is the variation in the time between the hardware event and the start of the ISR code. Sources: (i) interrupt latency of the core (12 cycles on Cortex-M for tail-chaining, more with flash wait states); (ii) higher-priority interrupts delaying the timer ISR; (iii) long critical sections with interrupts disabled; (iv) DMA bus contention; (v) the ISR itself taking longer than the period, causing overrun. Mitigation: keep the timer ISR minimal (set a flag or push to a queue, do the work in the main loop), use hardware capture or DMA instead of interrupt-driven sampling, give the timer an appropriate pre-emption priority, and avoid disabling interrupts for long periods.
Q12. Your board resets randomly every few hours. How do you diagnose it?
Start by reading the reset-cause flags in the RCC/PMU registers (power-on reset, brown-out, watchdog, software reset, pin reset). If it is a watchdog reset, the firmware is locking up; if it is a brown-out, suspect the power supply, inrush current from a radio transmitter, or an inadequate decoupling capacitor. Then: enable the hard-fault handler and log the stacked PC, LR and xPSR to non-volatile memory so you can identify the faulting instruction; check the stack high-water mark; run the system with the watchdog enabled and log the task/state at the moment of the kick. In the majority of field reports this pattern is a stack overflow or a heap exhaustion triggered by an edge-case input.
Q13. In a FreeRTOS design, why does each task need its own stack, and how do you size it?
Each task has an independent context (registers, return addresses, locals) and the scheduler may switch tasks at any time, so each task must own a separate stack region. The size must cover the deepest call chain of that task plus its local variables, plus the context saved by the scheduler (and by the FPU if floating point is used). Practical method: start with a generous estimate, run the system under worst-case load, then read uxTaskGetStackHighWaterMark() and set the stack to about 1.3–1.5× the peak observed usage. Interrupts run on the main stack (MSP), not on task stacks, so the MSP size must also be validated separately.
Q14. A DMA transfer into an SRAM buffer occasionally produces corrupted data on a Cortex-M7. What is the likely cause?
Cache coherency. If the buffer lies in a cacheable region, the CPU may read a stale cached copy while DMA has written new data straight into SRAM (bypassing the cache), or the CPU may hold dirty cache lines that overwrite the DMA result. Fixes: (1) place DMA buffers in a non-cacheable region (MPU-configured or a dedicated SRAM bank) as the cleanest solution; (2) otherwise, clean (flush) the cache before starting a transmit DMA and invalidate it after a receive DMA completes; (3) ensure the buffer is aligned to a cache line (32 bytes on Cortex-M7) and that its size is a multiple of the cache line, to avoid invalidating neighbouring variables.

Industry perspective

In real product development these two topics appear together constantly. A motor-control firmware engineer spends most of the day on timer configuration — centre-aligned PWM with dead-time insertion for a three-phase inverter, ADC triggering synchronised to the PWM carrier, and input capture for rotor position. A firmware engineer working on a battery-management or automotive ECU spends most of the day on memory: static allocation with pools, MPU-protected stacks, linker-script placement of safety-critical data in a redundant RAM bank, and runtime stack monitoring reported to a diagnostic trouble code. Validation engineers write tests that specifically stress these paths — maximum ISR nesting, minimum free heap, worst-case interrupt storm — because that is where field failures come from.

10.2 Where memory management is critical

  • Automotive ECUs: MISRA C compliance, MPU-protected task stacks, static-only allocation, ECC-protected RAM, and redundant copies of safety-critical variables.
  • Medical devices: deterministic memory footprints documented for certification, stack analysis for every ISR, and no dynamic allocation after initialisation.
  • IoT sensors: fixed ring buffers for radio packets, DMA buffers placed in non-cacheable RAM, and aggressive low-power use of the heap during deep sleep (RAM retention domains).
  • Networking stacks (lwIP, BLE): packet buffer pools (pbuf pools) with reference counting instead of malloc, exactly to avoid fragmentation under sustained traffic.
  • Bootloaders: carefully link-time-placed vector tables, flash-write buffers, and a linker script that reserves a region for the application image.

10.3 Design considerations and common implementation challenges

Timer design challenges

  • Timer peripheral sharing between incompatible functions
  • Glitches when updating ARR/CCR without preload
  • Counter wrap handling in long-interval software timers
  • Clock-source accuracy and temperature drift (RC vs crystal)
  • Reduced timer clock frequency in low-power modes

Memory design challenges

  • Stack sizing under worst-case ISR nesting
  • Heap/stack collision with no MMU protection
  • Cache coherency with DMA on Cortex-M7
  • Alignment and endianness for structures shared with hardware
  • Flash wear-out when using emulated EEPROM

12.2 Important definitions at a glance

  • Prescaler: a divider inserted between the clock source and the counter.
  • Auto-reload: the value at which the counter wraps and the update event fires.
  • Capture/compare register: dual-purpose register for PWM duty or latched count.
  • Stack: LIFO storage for function frames and interrupt context; grows downward on ARM Cortex-M (full-descending).
  • Heap: dynamic-allocation region; grows upward, toward the stack.
  • Fragmentation: free memory that exists but cannot satisfy the request.
  • Deterministic allocation: allocation whose worst-case time is bounded and independent of history.

12.5 Memory aids

  • "T = R × P / f" — Time = Reload count × Prescaler / frequency.
  • "+1 always" — both PSC and ARR contribute a +1 because the counter passes through (ARR+1) states and the divider has (PSC+1) values.
  • "data is doubled, bss is free of flash" — .data costs Flash + RAM; .bss costs RAM only.
  • "heap up, stack down" — they grow toward each other; the gap is your safety margin.
  • "Pools, not malloc" — fixed-size blocks never fragment.
  • "Capture measures, compare generates" — a quick mnemonic for CCR usage.

13.5 Limitations and assumptions

  • Register names follow the widely used STM32 / ARM Cortex-M convention. Other vendors (TI MSP430, Microchip PIC, NXP LPC) use different names for equivalent functions; the underlying principles and equations are unchanged.
  • The centre-aligned PWM formula uses the STM32 reference-manual convention (2·ARR). Some textbooks write 2·(ARR+1); the difference is one count and does not change the engineering conclusion.
  • Timer equations assume an ideal, jitter-free clock. Real designs must budget for oscillator tolerance, PLL jitter and interrupt latency.
  • Memory-map addresses (0x0800_0000, 0x2000_0000) are illustrative of a typical Cortex-M device and are not tied to a specific part number.
  • Stack and heap sizing recommendations follow common industry practice (30–50 % margin) but must be validated by measurement on the actual target hardware.
